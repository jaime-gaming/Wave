# Web backup format and safety

**Status:** WAVEBK2 is implemented for web only; native applications do not yet read or write it. WAVEBK1 remains readable as a legacy, unencrypted and unsigned archive. Neither format is a cloud service. Keep original files and test recovery before relying on an export.

## WAVEBK2 layout

- Bytes 0–7: ASCII `WAVEBK2\n`; bytes 8–11: little-endian unsigned JSON header length. The header is at most 2 MiB.
- The UTF-8 JSON header has `signed` and `signature`. `signed` has ordered properties `version` (2), `publicKey` (hex uncompressed 65-byte P-256 point), `salt` (16-byte hex), `nonce` (8-byte hex), `size` (plaintext byte count), and `hashes` (ordered SHA-256 hex digests of encrypted chunks). `signature` is the 64-byte raw IEEE P1363 `r || s` ECDSA P-256/SHA-256 signature, hex encoded, over UTF-8 `JSON.stringify(signed)` bytes. Exact property order and compact JSON serialization are part of this version's signature contract. Unrecognized or malformed data must fail closed.
- The payload is consecutive AES-256-GCM ciphertext chunks (1 MiB plaintext each except the last, each followed by its 16-byte tag). The 96-bit IV is the random 8-byte nonce followed by the chunk index as a big-endian uint32, starting at zero. The key is PBKDF2-HMAC-SHA-256 of the UTF-8 password, random 16-byte salt, 600,000 iterations. There is no additional authenticated data; the signature binds the nonce, salt, size, order and SHA-256 hash of every ciphertext/tag. Total plaintext is limited to 16,384 MiB. Password input is limited to 1,024 UTF-8 bytes.
- Plaintext is exactly a WAVEBK1 archive. That archive starts with `WAVEBK1\n`, a little-endian uint32 manifest length (maximum 32 MiB), UTF-8 JSON manifest version 1, followed by consecutive original audio bytes described by offsets and lengths. Settings, linked devices, folder handles and the backup signing key are excluded.

A synthetic, publicly known password and test vector live in `src/data/backup/fixtures/v2.json`. Its fixed salt and nonce are test data only. The Windows contracts include an experimental WAVEBK2 verifier/decryptor for this vector, **not** an integrated backup or restore feature. It writes untrusted plaintext to a staging stream: callers must discard that stream on every failure and validate the entire WAVEBK1 payload before touching a library. The verifier currently accepts the canonical web V2 signed-header schema only. Native export, restoration, rollback and content parity remain unimplemented; the vector alone does not establish cross-platform compatibility.

The header reveals the signing public key, archive size and number of chunks; music and metadata are encrypted. Each export uses a fresh salt and nonce. Password strength matters: choose a long unique password and keep it separately. Wave cannot recover it. A signature verifies that whoever holds the private key signed these exact encrypted chunks; it does **not** establish the person's identity or independently trust a device. Compare the full public-key SHA-256 fingerprint with one obtained separately from the original device. Clearing app data changes the device identity; old signed backups remain decryptable but must be compared with the previously recorded fingerprint. A compromised browser/origin or device can use its stored non-extractable key.

## Review and restore

Verification rejects malformed headers, invalid public keys/signatures, ciphertext hash changes, bad GCM tags, truncation and trailing bytes. A wrong password or altered data never writes to IndexedDB. The archive is checked for record shape, duplicate record keys and valid contiguous audio bounds. On review, byte-identical local audio and repeated YouTube references are counted using actual bytes/IDs rather than trusting metadata. The user can optionally skip them: Wave keeps the first song's metadata and remaps playlist, album-order and listening references. With that option off, it preserves all records. Similar titles or different encodings are not exact duplicates.

Restoration remains all-or-nothing into an empty web library, checked again in the write transaction including remembered folders. Close other Wave tabs; storage/quota failures abort the transaction. There is no selective repair, merge with an existing library, native interoperability or recovery of missing/corrupted chunks. WAVEBK1 structure checks cannot prove its integrity or source.

Encryption is chunked to limit individual cryptographic buffers, but export and restore create complete Blob representations and duplicate detection hashes a complete song at a time (up to the 200 MiB import limit). Large collections need significant storage/memory and can fail safely; this is not an unbounded streaming archive. Browser WebCrypto and IndexedDB support in a secure context is required. The format has not received an independent cryptographic audit.

## Work needed before claiming cross-platform support

Each native application needs production export and import, mapping of every supported track, playlist, artwork, artist, album, history and settings field (with explicit reporting for unsupported data), safe staging and atomic rollback, the same fingerprint confirmation and duplicate policy, and a usable restore flow. Acceptance requires real round trips in both directions across platforms, wrong-password, tampering, truncation, quota and interrupted-restore tests, plus native UI and device validation. A shared envelope or synthetic fixture is not equivalent to full library interoperability.
